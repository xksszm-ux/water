# 项目面试讲解提纲

使用前提：只讲自己实际参与和能解释的部分。下面描述的是代码、设计和本轮软件检查事实，不代表个人已经完成硬件调试。详细证据见 [工程说明](ENGINEERING.md) 和 [验证记录](../software_checks/README.md)。

## 约三分钟的整体介绍

这个项目是STM32F103与ESP32组成的双主控机器人原型，目前还没有通过硬件验收。本轮重点是把软件作为一个整体整理，补齐通信和控制边界、回归测试与诊断，不把编译通过说成整车完成。

分工上，STM32负责电机输出、传感采集、电池保护和控制仲裁；ESP32负责BLE连接、授权、UART握手及状态展示。这样能把无线协议栈与底层输出职责分开，但代价是必须维护双端协议，并处理断线、旧命令和状态过期。目前BLE保持STOP-only，CAN/AUTO非零运动也在STM32仲裁入口安全拒绝，避免先接受、再被ESP32的全局STOP打断。内部UART运动路径保留，但不能说整车运动已完成。

STM32有7个常驻业务任务。电机任务每10毫秒处理一次，优先级最高，命令超过300毫秒就清除并停车；串口与CAN任务通过事件唤醒；传感器、电池按各自周期采样；显示和Flash日志优先级低，避免慢I/O进入控制任务。电机命令用单槽覆盖队列，只保留最新目标；STOP另用独立原因位，避免被运动命令覆盖。MPU6050和OLED共用I2C互斥锁，其他资源尽量由单个任务拥有。

串口接收不是简单地“用了DMA”。STM32使用64字节循环DMA，IDLE和传输完成回调把新字节搬进软件环形缓冲，再由任务按帧头、版本、类型、序号、长度和CRC解析。IDLE只是唤醒条件，不是帧边界，所以还要处理半帧、粘包、噪声、坏CRC和缓冲溢出。

这轮在电脑端确实复现了两个问题。一个是把时间戳零当成没有样本，导致有效传感数据不再过期；另一个是新字节先刷新半帧计时，使迟到的尾部字节复活旧帧。新增测试先在旧代码上失败，再修改生产代码并通过回归。它们是软件复现，不是实机故障故事。

稳定性方面，当前通过STOP优先、命令期限、电池门控、状态新鲜度和重连握手限制错误影响，并把STM32的任务栈、堆、锁存的任务健康故障及通信错误传到ESP32串口。软件检查已扩展至25组，新增PVD/电机、ADC DMA、超声波、I2C/SPI及完整BLE源码事件检查；实际执行与环境阻塞以验证记录为准，不能说所有运行条件已验证。任务健康期限仅按代码阻塞路径静态估算，真实调度、NimBLE/RF、硬件停车和长期运行仍待验证，硬件看门狗也还没有启用。

**为什么不直接让ESP32接受CAN非零状态？**

本轮保留既有STOP-only保护。在连续软件场景中确认CAN先被接受、ESP32再要求STOP的冲突后，选择在共用仲裁入口拒绝CAN运动；代价是CAN独立运行也被限制。另一方案是定义受控运动许可并同步修改ESP32策略，工作范围和安全验证要求更大；把STOP改成只停止UART所有者则会削弱全局停止。CAN运动仍无ACK，现通过独立UART 0x83和加密BLE读取报告最新决策、序号、拒绝/重放累计数，明确区分不可用与尚无事件；连续软件检查通过，真实读取未验。反馈可覆盖旧事件，不能当逐命令ACK。代码及复现见工程说明B7，不能把软件输出清零说成车轮停车。

## 追问：选型不是背关键词

**为什么不用一颗ESP32？**

单ESP32是合理替代方案，能减少板间通信和固件维护。本项目已经有STM32驱动、定时器/PVD控制及ESP32 BLE代码，保留双主控能延续现有分工。不能只说“两颗更稳定”，也不能保证无线栈与控制之间存在硬件级故障隔离；实际供电、串口异常和复位耦合还没验收。

**DMA一定比中断好吗？CPU降低多少？**

本项目关注不定长输入与每字节ISR开销，DMA允许批量搬运，任务做协议解析。但它增加环形位置、覆盖和缓存一致性的处理；没有测量就不报CPU降低百分比。小吞吐场景逐字节中断也可能足够。

**为什么IDLE不是一帧？**

发送方可在半帧暂停，也可连续发送多帧。只有协议头部长度和CRC才能验证帧。IDLE唤醒解析任务；DMA TC也能在持续数据流中唤醒。代码见 [UART驱动](../stm32/Drivers/UART/uart_driver.c) 和 [解析器](../stm32/Application/Services/Protocol/protocol.c)。

**缓冲区为什么是64和256？**

这是现有资源预算，64B DMA和255B可用软件环在115200/8N1满线速下分别约覆盖5.56ms和22.14ms；还要考虑10ms任务等待、8帧处理预算和抢占。它们不是经过压力测试证明的最优大小；后续应结合overflow计数和最坏调度延迟调整，不盲目扩大RAM占用。

## 追问：FreeRTOS任务设计

**为什么是7个任务？**

答案要结合不同期限与阻塞源：Motor每10ms且最终控制输出；Comm/CAN事件驱动；Sensor会等待I2C；Battery慢采样；Display和Storage可能长阻塞。7不是目标数字，也不是调度器全部任务：启动任务会退出，内核仍有Idle/Timer。完整表见 [任务设计](ENGINEERING.md#4-freertos-任务设计)。

**优先级怎么定？**

Motor为AboveNormal；通信/CAN/Sensor为Normal；Battery为BelowNormal；Display/Storage为Low。依据是输出时限与慢I/O影响，尚未用实测WCET证明可调度。电池任务即使延误，Motor会在数据过期后保守停机；这不能替代调度验证。高优先级任务必须阻塞或有处理预算，不能永久忙循环。

**队列、信号量、互斥锁、通知如何选择？**

队列传递命令/样本；本项目需要最新值，选择1槽覆盖而非累积旧目标。STOP是独立事件位。UART字节在缓冲里，通知只唤醒唯一任务；不拿通知承载大数据。I2C需要资源所有者和优先级继承，用mutex，二值信号量并不等价。ESP32的BLE生命周期使用事件组等待成功/失败/退出等组合条件。不能说项目所有地方都用了同一种机制。

**什么是优先级反转，这里怎么处理？**

低优先级Display拿I2C锁，Normal的Sensor等它；如果其他中优先级任务持续抢占Display，会延长Sensor等待。底层FreeRTOS mutex的优先级继承可临时提升持锁者，减少这一段干扰。但它不能缩短I2C外设耗时、不能打破死锁，也不会在osDelay时释放mutex。代码分页刷新；MPU初始化仍跨100ms持锁，是明确限制。

**任务和中断有什么区别？**

ISR抢占执行，不能做普通阻塞等待；只搬有界数据、记事件，使用允许的ISR通知接口。任务可以按优先级被调度、等待队列/锁，再做CRC和协议语义检查。STM32外设IRQ设5，PVD设4；PVD比RTOS可调用阈值更紧急，只做紧急寄存器停车，不调用队列或通知API。

**临界区和挂起调度器有什么区别？**

STM32任务临界区用于短共享字段更新，屏蔽到RTOS规定中断阈值，不代表所有中断都关；挂起调度器只暂停任务切换，中断继续。仲裁用挂起调度器把所有权决定和非阻塞队列提交串起来；PVD仍能打断。ESP32多核不能只依靠单核调度挂起，共享字段使用portMUX保护，锁里不做阻塞I/O。

**栈大小怎么定？**

先看调用链和局部数组，再看编译器`.su`报告，最终用最坏场景下的高水位校验并保留余量。本轮保留STM32大部分任务512B、Comm640B；没有硬件数据不能说够用。CMSIS栈参数是字节，底层ARM FreeRTOS高水位是word，本项目乘4；ESP-IDF任务创建栈参数是字节。不能只背“stack depth”的名词。

**tick和软件定时器呢？**

STM32是1kHz，代码以tick当ms，本轮加了编译断言；ESP32本次100Hz，使用pdMS_TO_TICKS。相对delay会把工作时间算入周期，固定周期任务使用绝对delayUntil并处理超期。软件定时器在共享服务任务执行，慢I/O会拖累其他回调，没必要为了增加技术点改用它；BLE已有NimBLE callout处理广播重试。

## 追问：真实bug怎么讲

选择B2讲一个完整闭环：

1. 预期：超过50ms的旧半帧不能拼成可执行命令。
2. 最小复现：直接执行生产通信任务处理函数，10ms喂前4B，71ms喂剩余6B；不模拟协议算法。
3. 旧代码现象：仍被接受，新增测试失败。
4. 原因：先PushByte更新last_byte_ms，再Next检查超时。
5. 修改：先处理旧解析缓冲，再读入新字节，保留有界处理预算；检查ESP32对应调用顺序。
6. 回归：迟到尾部被丢弃，随后完整帧可恢复；坏CRC、长度和回绕仍通过。
7. 限制：时间来自任务观察，没有每个UART字节的硬件时间戳，真实DMA和任务拥塞还没验收。

证据见 [communication_checks.c](../software_checks/integration/communication_checks.c)，不是“遇到问题后加一个delay就好了”。B1的证据见 [control_checks.c](../software_checks/logic/control_checks.c)。如果不是你亲自定位，不要改写为自己的个人经历。

## 追问：稳定性如何保证

更准确的回答是“通过哪些机制限制故障，以及目前验证到哪一层”，不能承诺绝对稳定：

- STOP独立优先，执行时清旧目标；新命令过期后停车。
- 电池数据无效/低压/过期禁止运动；恢复需要新命令。
- 链路恢复必须匹配本轮STOP ACK并等更新的零输出状态；ACK只表示受理。
- 队列、解析与I/O有边界和错误计数，诊断能传到ESP32串口。
- 可运行测试覆盖上述决策逻辑，真实并发/时序/设备效果仍未验证。
- 当前IWDG未启用；若MotorTask本身卡死，软件超时检查可能无法执行，这是明确缺口。后续按关键任务心跳监管喂狗，并验证复位时输出安全。

不能说“跑了几天没问题”“所有任务不会溢栈”“DMA没有丢包”“车轮一定300ms内停下”。这些都需要实际证据。
